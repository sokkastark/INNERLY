# INNERLY — Initial Product & Engineering Brief

We are building **Innerly**, an India-first educational and decision-support Progressive Web App (PWA) focused entirely on **innerwear knowledge and guidance**.

## 1. Product Vision

Innerly helps people understand:

* what different types of innerwear are
* why different types exist
* where and when they are useful
* how innerwear relates to the wearer's body
* how innerwear works with different outerwear
* how occasion, activity, comfort and fabric affect the choice
* what common fit/comfort/visibility problems mean
* how to make an informed decision independently

Innerly is **NOT an online store**.

Innerly is **NOT a lingerie brand**.

Innerly is **NOT primarily a shopping website**.

Innerly is **NOT a chatbot-first product**.

Innerly is a **free educational and guided recommendation tool**.

Product recommendations may be added later as a secondary, optional feature. They must never drive the product experience. If affiliate requirements conflict with Innerly's user-first philosophy, recommendations/affiliate functionality must be removable without affecting the core application.

The core value of Innerly must remain useful even with zero commercial links.

---

# 2. Product Philosophy

The fundamental principle is:

> **Educate first. Guide second. Let the user decide.**

Never manipulate the user into:

* clicking
* purchasing
* continuing a flow
* watching content
* opening external links

Avoid:

* forced popups
* misleading buttons
* dark patterns
* autoplay
* fake urgency
* aggressive affiliate CTAs
* intrusive advertising

The user should always understand:

* where they are
* what they are learning
* why a recommendation was made
* what they can do next
* how to leave the flow

---

# 3. Target Platforms

Innerly is a **PWA**, not a native Android application.

Target:

1. Mobile — primary
2. Tablet
3. Desktop

The implementation must therefore be fully responsive.

Do NOT create separate mobile and desktop applications.

Use one responsive application with adaptive layouts.

The PWA should support:

* installability
* responsive layouts
* appropriate manifest configuration
* service worker/offline capability where appropriate
* fast loading
* accessible touch interactions
* keyboard/mouse interactions on desktop

# 9. Recommendation Philosophy

The recommendation system should NOT initially be an AI system.

Build a deterministic, explainable recommendation architecture first.

Conceptually:

INPUT
→ relevant knowledge
→ rules
→ scoring/considerations
→ recommendation
→ explanation

Example:

Outerwear + Occasion + User preference
→ relevant innerwear characteristics
→ matching rules
→ recommendation
→ "Why this may work"

The system must be explainable.

Avoid black-box recommendations in the initial implementation.

---

# 10. Future Expansion

Architect for future capabilities without implementing everything now.

Possible future features:

* more advanced recommendation engine
* scoring
* confidence indicators
* saved journeys
* personalization
* optional affiliate product references
* community knowledge
* AI assistance

Do NOT implement future features merely because the architecture could support them.

Build only what is required for the current milestone.

---

# 12. Engineering Standard

Use:

* TypeScript
* strict typing
* reusable components
* feature-oriented architecture
* domain-oriented data structures
* separation of UI, business logic and data
* accessible semantic HTML
* responsive design
* testable business logic
* maintainable documentation

Avoid:

* giant components
* duplicated components
* hardcoded recommendation logic inside JSX
* hardcoded content scattered throughout pages
* deeply coupled components
* unnecessary global state
* magic numbers
* inline business rules
* copy-pasted UI

---

# 13. File Size Rule

No source code file should exceed **500 lines**.

If a file approaches the limit, refactor it into:

* smaller components
* hooks
* services
* domain modules
* utilities
* data modules

Do not artificially split files just to satisfy the number. Split according to responsibility.

---

# 14. Important Principle

Do not over-engineer Innerly.

Architecture must support growth while keeping the MVP understandable.

Every abstraction must have a reason.

Before adding a new library, framework, service or dependency, evaluate whether the existing stack can solve the requirement.
